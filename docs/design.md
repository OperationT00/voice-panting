# Voice Painting 设计文档

## 1. 项目目标

本项目选择题目二“AI 语音绘图工具”。目标是实现一个用户主要通过语音完成绘图创作的 Web 应用。

当前版本的核心目标不是做复杂专业绘图软件，而是先打通一条可扩展的语音绘图链路：

```text
语音输入
  -> 语音识别为文字
  -> 指令解析 / 模板匹配 / LLM 规划
  -> 结构化绘图动作
  -> SVG 画布执行
```

同时额外实现了 AI 生图模式：

```text
语音输入
  -> 语音识别为文字
  -> Qwen-Image 生图
  -> 展示参考图片
```

这样项目同时具备“可编辑 SVG 绘图”和“快速生成参考图”两种能力。

## 2. 技术选型

### 前端

- React + TypeScript：适合快速构建交互式工具，类型约束也方便维护指令结构。
- Vite：启动快，便于开发和演示。
- SVG：每个图形都是独立可编辑对象，适合后续支持“修改第二个圆”“删除左侧矩形”等语音编辑操作。
- Web Speech API：浏览器内置语音识别能力，MVP 阶段不需要额外搭建语音识别服务。
- SpeechSynthesis API：用于执行完成后的语音反馈。

### 后端代理

- Vite middleware：本地开发阶段提供 `/api/plan` 和 `/api/image` 代理接口。
- OpenAI-compatible Chat Completions：用于把复杂自然语言转换成结构化 `DrawingPlan`。
- DashScope / Qwen-Image：用于 AI 生图模式。

### 测试

- Vitest + Testing Library：覆盖指令解析、绘图 reducer、模板、LLM provider、图片 provider 和 App 交互。

## 3. 已计划的用户故事

最初计划支持以下用户故事：

- 用户可以通过语音创建基础图形。
- 用户可以通过语音修改已有图形。
- 用户可以撤销、重做、清空和导出作品。
- 用户可以通过复杂指令生成组合图形。
- 系统可以把复杂指令拆解成多个小绘图步骤。
- 常见图形可以沉淀为模板，减少重复模型调用。
- 用户可以在不方便说话时通过文字模拟语音输入。
- 用户可以调用 AI 生图模型生成参考图。

## 4. 最终已实现功能

### 4.1 语音与文字输入

已实现：

- 使用浏览器麦克风进行语音识别。
- 支持文字输入模拟语音。
- 语音和文字输入复用同一套指令处理逻辑。
- 模型处理时显示加载动画，并禁用输入避免重复提交。

未完全实现：

- 暂未接入服务端语音识别模型。
- 暂未实现连续多轮语音对话上下文。

原因：

- 浏览器 Web Speech API 已能满足 MVP 演示。
- 本项目重点放在“语音指令到绘图动作”的链路验证。

### 4.2 SVG 绘图

已实现：

- 支持创建圆、矩形、三角形、线条、文字、椭圆、菱形、星形、路径 `path`。
- 支持颜色、大小、位置、旋转、描边颜色、描边粗细。
- 支持撤销、重做、清空、导出 SVG。
- 支持动作日志和 Action JSON 展示。
- 支持坐标化布局，画布内部使用 `0-1000`、`0-560` 的坐标范围。

未完全实现：

- 暂未实现自由手绘笔刷。
- 暂未实现拖拽式手动编辑。
- 暂未实现复杂图层面板。

原因：

- 题目要求是纯语音控制，当前优先保证语音操作闭环。
- SVG 对象化编辑已经足够支撑后续语音微调。

### 4.3 图形编辑与微调

已实现：

- 按目标修改图形，例如“第二个圆”“刚才的图形”“所有红色图形”。
- 支持移动、放大、缩小、旋转、改颜色、加粗线条、变细线条。
- 支持置顶、置底、删除。
- 支持“把苹果梗变细”这类模板内局部微调。

未完全实现：

- 暂未实现任意部件的精准语义定位。
- 暂未实现“把房子的窗户往左一点”这种更细粒度对象理解的完整覆盖。

原因：

- 当前已经有目标解析和模板部件 id，后续可继续扩展语义部件映射。

### 4.4 模板库

已实现：

- 内置模板库，当前包括房子、苹果、火箭等模板。
- 模板保存为结构化 `DrawingPlan`，可以直接展开为绘图动作。
- 支持语音保存模板，例如“保存此模板”。
- 用户模板存储在浏览器 `localStorage`。
- 绘图时优先命中本地规则和模板，未命中再走 LLM。

未完全实现：

- 暂未实现云端模板库。
- 暂未实现模板分享、搜索、版本管理。
- 暂未实现模板质量评分和自动沉淀。

原因：

- 本地模板已经能验证“低成本复用”的核心思路。
- 云端模板涉及账号、存储和权限，超出当前 MVP 范围。

### 4.5 LLM Planner

已实现：

- 支持通过 `/api/plan` 调用 OpenAI-compatible 大模型。
- 通过 prompt 约束模型只输出结构化 `DrawingPlan`。
- `DrawingPlan` 会经过 schema 思路、运行时校验和 action pipeline。
- 支持失败修复：模型第一次输出非法计划时，会再次请求模型修复。
- 支持意图校验：减少“画机器人却输出问号”等错误。
- 支持 Qwen / DeepSeek 等兼容 Chat Completions 的模型配置。

未完全实现：

- 暂未实现真正多轮 ReAct 循环中的观察、纠错和再次绘制。
- 暂未实现模型对当前画布的视觉理解。
- 暂未实现自动评估绘图是否“像用户要求的对象”。

原因：

- 目前 LLM 主要负责“语言到结构化计划”。
- 多轮视觉评估需要额外接入多模态模型和截图分析，成本更高。

### 4.6 AI 生图

已实现：

- 支持 `SVG 绘图 / AI 生图` 模式切换。
- AI 生图模式下，语音或文字输入会调用 `/api/image`。
- `/api/image` 后端代理调用 DashScope / Qwen-Image。
- 前端展示生成图片和 Result JSON。
- API key 只在服务端代理读取，不暴露给浏览器。

未完全实现：

- 暂未把生成图片自动转换为 SVG 可编辑对象。
- 暂未实现“根据图片临摹成简笔画动作”的完整链路。

原因：

- 文生图生成的是位图，和当前 SVG 可编辑对象不是同一种数据结构。
- 后续需要引入多模态理解或图像矢量化能力，再转成 `DrawingPlan`。

## 5. 系统链路

### SVG 绘图链路

```text
用户语音 / 文字
  -> Web Speech API 或文字输入
  -> 本地规则解析
  -> 模板匹配
  -> LLM Planner fallback
  -> DrawingPlan / DrawingAction
  -> validateAction
  -> reducer 更新画布
  -> SVG 渲染
```

### AI 生图链路

```text
用户语音 / 文字
  -> Web Speech API 或文字输入
  -> /api/image
  -> DashScope / Qwen-Image
  -> 图片 URL
  -> 前端展示
```

## 6. 成本控制策略

计划采用的成本控制策略：

- 优先本地规则解析，简单指令不调用模型。
- 常见复杂图形沉淀为模板。
- 模板命中优先于 LLM 调用。
- LLM 只输出结构化计划，不让模型直接生成图片，减少 token 和重试成本。
- 图片生成独立为 AI 生图模式，避免每次 SVG 绘图都触发高成本图片模型。
- API key 只放后端代理，避免前端泄露。

实际已采用：

- 本地规则优先。
- 内置模板优先。
- 用户模板本地保存。
- LLM fallback 只在本地无法识别时触发。
- `/api/plan` 和 `/api/image` 都通过服务端代理读取密钥。
- 生图模式和 SVG 绘图模式分离。

暂未采用：

- 云端缓存模型结果。
- 模板质量评分。
- 用户级调用限额。
- 图片生成结果复用和 CDN 缓存。

原因：

- 当前是单机 MVP，本地缓存和模板已经能展示成本控制思路。
- 云端缓存和限额需要后端账号体系，适合后续产品化阶段。

## 7. 当前不足与后续计划

当前不足：

- 复杂图形的美观度仍依赖模板和 LLM 输出质量。
- LLM 生成的 SVG 计划不一定每次都足够形象。
- 用户模板只保存在浏览器本地。
- AI 生图结果还不能直接变成可编辑 SVG。
- 浏览器原生语音识别在不同系统上的稳定性可能不同。

后续计划：

- 增强模板库，覆盖更多常见简笔画对象。
- 引入“计划 -> 执行 -> 观察 -> 修复”的 ReAct 循环。
- 使用多模态模型分析生成图或画布截图，再反向生成更好的 `DrawingPlan`。
- 增加云端模板库和模板搜索。
- 增加更细粒度的部件语义，例如“车轮”“窗户”“苹果梗”。
- 增加调用成本统计和缓存策略。
